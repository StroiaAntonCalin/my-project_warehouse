# Step 5: Technical Constraints

## Objective

Document known constraints with status, impact assessment, and source information.

## Entry Criteria

- [ ] Step 4 (System Map) complete with confirmed system architecture

## Actions

### 5.1 Document Constraints

Create constraint inventory with status tracking:

```
Technical Constraints

| Constraint | Source | Status | Impact | Notes |
|------------|--------|--------|--------|-------|
| **[Constraint 1]** | Client requirement / Regulatory / Technical | ✅ Confirmed | High/Medium/Low | [Additional context] |
| **[Constraint 2]** | [Source] | ⚠️ Assumed | High/Medium/Low | [Additional context] |
| **[Constraint 3]** | [Source] | ❌ Open | High/Medium/Low | [Additional context] |

Status Legend:
- ✅ Confirmed = Validated with stakeholders
- ⚠️ Assumed = Inferred from Signal, needs validation in SP2
- ❌ Open = Unknown, requires stakeholder input

Impact Levels:
- High = Blocks progress, requires immediate resolution
- Medium = Affects design decisions, needs consideration
- Low = Minor constraint, workarounds available
```

**STOP**: Wait for human to validate constraints.

## Exit Criteria

- [ ] All known constraints documented
- [ ] Each constraint has source, status, and impact
- [ ] Status uses ✅/⚠️/❌ classification
- [ ] Human validated constraints
